Old ideas. Fresh trouble.

not a command

Things ftnt could grow into.

A pile of proposals. The six commands stay as they are until one of these is chosen on purpose.

00

How to read this

Each idea is a separate command, or an explicit refusal to add one. Pipes stay the composition tool. A command either reads a base, writes a base, or filters text. Mixing those in one invocation is how a tidy tool becomes a tosser.

Nothing here is scheduled. The crooked shelf and the toys are included because a boring shortlist hides the interesting edges. Shipping a toy would be a decision, not a joke that leaked into --help.

Constraints that already exist, and that every idea below has to live with:

  • Bases are offline. GoldED and every other user are closed first. A lock is not a promise of safe sharing.
  • Format packages own bytes, locks, encoding and rollback. The CLI does not grow a second serializer.
  • write input is not an export envelope. Dates, addresses and control lines keep the rules they have now.
  • Export is data, not a byte-identical backup. Reply links are not repaired on the way in.
  • repair stays opt-in. Import and export do not quietly heal text.
  • Opus dates, and any write GoldED is expected to open afterwards, stay unverified until someone actually does that.
01

Convert

ftnt convert SRC DST --to squish

The hole people will fill with a shell script. export prints an envelope. write refuses envelopes. Dates that are legal in JAM are illegal in Opus, and Squish demands a timezone the MSG writer will not take. A script that strips fields and hopes is how a fixture quietly loses a MSGID.

--from is optional. Without it, convert tastes SRC and chooses the reader. The taste is the files that are actually there, not a guess at the contents of a random byte:

  • JAM when the .JHR, .JDT and .JDX companions are present.
  • Squish when the .SQD and .SQI companions are present.
  • Hudson when MSGHDR.BBS, MSGIDX.BBS and MSGTXT.BBS are present in that directory.
  • A .MSG directory when it contains numbered .MSG files and none of the sets above.

Two smells at once is a refusal, exit 2, naming both. A directory that is both a JAM base and a pile of .MSG files does not get a silent preference. --from is how you break that tie, and how you override a taste you do not believe.

Opus and FTSC are the smell the directory cannot settle. Both are numbered .MSG files. The header difference is inside the file, and a confident Opus-versus-FTSC guess would be a second parser living in the CLI. A .MSG directory therefore tastes as msg. --from opus is required when the headers are Opus. Getting that wrong is a bad read, so the plan printed before --apply repeats the chosen source format in a form you can stop.

--to stays required. The destination often does not exist yet, and an empty path has nothing to taste. Tasting DST when it already has a base is a later refinement, and only as a check that --to agrees with what is already there. A disagreement refuses. Convert does not switch destination format because the old files looked like JAM.

convert reads with the source reader and appends through the destination writer, one message at a time, same as write: structural rejection before the writer opens, then one commit per message, then a receipt. It does not stream the envelope through stdout and back through stdin. The translation is the command.

Before the first append it prints a plan on stderr, not a success: which fields will be dropped, which dates will be rewritten, which messages it already knows it must refuse. --apply is what actually writes. Without --apply the destination is not created and not opened for write. That is the whole safety model. A convert you cannot preview will be run twice, and the second run duplicates the base.

Refusal rules worth keeping:

  • Hudson still needs --board on the side that is a single board. Converting a whole Hudson file onto one board without saying so is a way to merge areas by accident.
  • A message whose date cannot be represented is skipped and counted, or the command stops. The choice is a flag, default stop. Silent skip is a data loss bug with a progress bar.
  • Control lines the destination writer will discard are named in the plan. Unknown controls are not renamed into something familiar.
  • Message numbers are the destination’s numbers. Reply links that pointed at source numbers are either dropped or rewritten only when the source number was actually copied and the map is complete. A half-rewritten thread is worse than a thread with no links.
  • No packet, no area file, no routing. Convert moves a base. It does not enter a netmail into a network.

The interesting version of the receipt is a map: source identity, destination identity, and a list of dropped field names. That map is what a later witness would hash.

02

Update and delete

Append-only is why write is allowed to be simple. The moment a command can replace or remove a message, a rerun is no longer “maybe a duplicate”. It can destroy the only copy.

ftnt update BASE MSGNO --format jam

Stdin is the same object write accepts, plus the revision read --revision already prints. The writer open uses that revision. A mismatch is exit 5, and the base is unchanged. No revision flag, no update. Guessing “the current message” from a number alone is how two scripts edit message 12 and the second one wins without noticing.

The command does not invent fields the writer cannot store. It does not offer a patch language. A jq edit of the read --revision object, stripped back to write fields, piped into update, is the workflow. Teaching update its own edit syntax would split the JSON contract in two.

ftnt delete BASE MSGNO --format jam --revision DIGEST

One message. The revision is required, same conflict rule. Stdout is a receipt with the identity that was removed, not the body. The body is not echoed “so you can undo”: that encourages people to treat stderr scrolls as backups.

There is no delete --all, no range, no “older than”. Ranges feel like housekeeping and behave like a bad evening. A loop in the shell can delete ten messages and can also be reviewed.

Soft delete, a kludge tombstone, a Deleted flag: only if the format package already has that operation. The CLI should not stuff a synthetic ^ADELETED into a body and call it gone. GoldED will show it as a message, which is the opposite of gone.

03

Thread

ftnt thread BASE MSGNO --format jam

Follow reply links from one message and write the thread as ordinary message envelopes, in an order that can be read aloud: root first, then replies. Cycles are reported and broken. Missing numbers are reader issues on stderr, not invented placeholder messages.

This is a read. It does not rewrite reply_to_msgno to “fix” a thread, and it does not run during write. The specification already refuses an automatic link resolver on import. Thread view is the part people actually want. Link repair is the part that corrupts history while feeling helpful.

Two orders are enough. --walk reply follows the chain the writer stored. A second mode can group by subject only when asked, and it must say that subject grouping is a guess. Mixing them by default produces a thread that never existed.

Hudson uses --board. A thread that jumps boards is out of scope until the reader exposes that jump as data. Inventing cross-board threads from subject lines is folklore.

04

Stat and sample

ftnt stat BASE --format hudson

One JSON object: format, resolved path, message count, lowest and highest number, and for Hudson the board numbers that actually occur. Optional, if the format package already exposes it: whether the base looks locked, and the lastread value. If the package does not expose lastread, the field is absent. A zero invented by the CLI is a lie a GoldED user will trust.

No per-message dump. That is export. stat is the thing you run before deciding an export is worth opening.

ftnt sample --format opus

Writes one minimal valid write object to stdout and exits. The date matches the format: naive for MSG and Hudson, timezone-aware for Squish, even seconds inside 1980–2069 for Opus. Names are obviously fake. The body says it is a sample.

This is the command that keeps the date table from being folklore in the manual. sample --format squish | ftnt write ./area --format squish should work on a base create just made. If it does not, the sample is wrong, not the user.

05

Lint

ftnt lint BASE --format msg

export --archive already continues past reader trouble and uses exit 7. Lint is the version aimed at a human who is not trying to save the messages. Stdout is one JSON object per finding. The base is not copied anywhere.

Findings that are worth the command, because they are tedious by hand and unambiguous:

  • Reader issues, the same objects archive mode already emits.
  • Duplicate MSGID values, listed with both message numbers.
  • Reply links whose target number is not in the base.
  • posted_at in the future relative to the clock the command is running on, and dates parked on the Opus epoch because a writer stored zeros.
  • Odd seconds on a base that claims to be Opus. That is a fact about the stored words, not a verdict that GoldED will reject the file.
  • A CHRS kludge naming a charset decode does not know.

Findings that should stay out, because they are taste: subject length, “too many seen-by”, empty bodies, messages to “All”. A linter that scolds echomail for looking like echomail will be ignored, and then so will the real findings.

Exit 0 when there are no findings, 7 when there are, same shape as archive export. Lint does not “fix” any of them.

06

Witness

ftnt witness BASE --format jam

A content hash of the export, not of the files. One JSON object: count, first and last number, and a digest over the canonical JSON of each envelope in number order. Paths are excluded from the digest. A witness that changes because you moved the directory is useless as a fixture check.

The point is regression for the format packages. Read a known base, store the witness next to the fixture, fail a test when a parser change alters text, kludges or dates. It is not a signature, not a MAC, and not a statement that two witnesses from different formats should match. Convert is lossy. Witnesses make the loss visible. They do not forbid it.

Canonical JSON has to be specified once: key order, UTF-8, no insignificant whitespace, dates already in the reader’s ISO form. If two versions of witness disagree about key order, every fixture looks corrupted.

07

Dialect and exorcist

ftnt dialect BASE --format msg

Report, per message, the charset the reader used and the CHRS kludge if one is present, when those two disagree. Optionally run decode’s strict decoder on the stored body bytes when the format package can hand those bytes over without the CLI reimplementing the frame. If it cannot, the finding says “kludge only” and stops. Guessing the original code page from Unicode is repair, and dialect must not call it.

ftnt exorcist BASE --format jam

The dry run of repair across every body_text. For each message where the heuristic would change something, emit the number, changed, confidence, and a short unified diff of the body. Write nothing. Confidence stays a number from 0 to 1.

A --apply that writes the repaired bodies back is a different command and a worse idea. It would hide the original bytes inside a format that may not be able to store them again, and it would make every later export look like the base had always been UTF-8. If apply is ever built, it belongs behind update’s revision check, one message at a time, after a human has read the diff. Exorcist itself never grows --apply.

08

The social life of a base

These are reads over the same envelopes export already produces. They earn a command only because the jq to do them is ugly and easy to get wrong. If the implementation is “export, then compute”, that is a feature. The CLI should not walk the binary twice with a second parser.

ftnt orphans BASE --format squish

Messages whose reply link points at a number the base does not have, plus messages that nothing points at, if you pass --roots. Roots are not errors. A base full of new posts is mostly roots. The default output is the broken links only.

ftnt gossip BASE --format jam

A histogram: who is addressed, who writes, which message numbers have the most replies, counted from stored links and not from “Re:” in the subject. Output is JSONL, smallest first or a --top cut. This is nosy and genuinely useful when you are trying to understand a borrowed echo before you convert it.

ftnt haunt BASE --format msg --quiet-since 1998-01-01

Addresses, nodes and points that appear in from-address or seen-by and whose newest message is older than the given date. It is a census of who stopped talking, not a routing table and not a suggestion to remove them. Seen-by lines from 1994 are historical. Deleting them to “clean” a base is vandalism with a sort key.

The command needs a real clock date on the CLI, and it must document the timezone it compares in. A haunt that treats naive MSG dates as local time on the machine running the command will accuse Danes and Californians of different ghosts.

09

Marks left by software

ftnt baggage BASE --format msg

Decode attributes_raw into flag names, but only names the core package already defines. Unknown bits stay as bit numbers. The CLI does not invent a friendlier vocabulary than the library. One row per message that has any flag set, plus a summary count. Private, crash, hold, file-attach and the rest are data. Baggage does not filter them out “for privacy”. If you export a base of private netmail, you already chose to read it.

ftnt origin BASE --format jam

Collect MSGID, PID, TID and tearline or origin lines when the reader has already split them into control lines or body text. Count them. The output is “GoldED 1.2.5 wrote 400 of these, unknown tearlines wrote 12”, which is the fastest way to learn whether a fixture is one program’s habit or a mess from six eras.

Do not scrape the body with a new regex if the reader already produced a control line. Two notions of “the origin line” will disagree in the one case you cared about.

10

The crooked shelf

Useful, a bit unwise, and each one needs a written reason to exist before any code.

ftnt carbon

Copy one message onto another Hudson board, or into another base, as a new append. It is convert for a single identity. The temptation is a --keep-number flag. Refuse it. Numbers are a property of the destination. Keeping them is how collisions get a command-line switch.

ftnt shrink

Read write-shaped JSON on stdin and emit a smaller object that write would still accept: drop empty arrays, drop nulls, optionally drop seen-by and path when --no-routing is set. This is a fixture tool. Point it at a live base and you have a way to launder routing history. The help text should say “fixtures”, and the command should refuse a --format base path so it cannot be aimed at mail.

ftnt curfew

A wrapper that refuses write when the payload breaks a format’s date rule, with a ruder message than the writer’s exception. This is only worth it if sample and write’s existing errors are still confusing after the manual. A second error string for the same rejection is clutter. A curfew that encodes policy the writer does not enforce is a bug. Opus even-seconds belong in the writer, where they already are.

ftnt adopt DIR --format msg

A directory of loose .MSG files is already what the MSG reader may mean by a base. Adopt is interesting only for a directory of text files that are not a base: one file per message, headers in a documented subset, bodies after a blank line. That is a new parser in the CLI. It violates the rule that format packages own serialization, unless the core grows an import for that text shape first. Without that, adopt is a tosser larval stage. Fun to describe, bad to start.

ftnt duel A.jsonl B.jsonl

Diff two exports that are already on disk. No base is opened. Compare by MSGID when both sides have one, else by number, and say which key was used. Field-level changes only: from, to, subject, date, body, controls. A duel that tries to be semantic (“these two bodies mean the same”) has become repair in a trench coat.

This one is crooked only because it does not need ftnt. A small program beside the manual would do. It earns a command if witnesses and converts start producing files people diff every day.

11

Toys

These do not belong in the default help. They are here so the idea has been had, and declined, in writing.

ftnt modem

Prints a connection banner, a baud rate it did not negotiate, and NO CARRIER, then exits 0 without reading stdin or touching a path. The entire point is that the command is obviously not a base tool. The risk is that someone asks for --dial next. If it ever exists, it lives behind an environment variable named something embarrassing, and it has no flags.

ftnt sysop

Rewrites diagnostics in the voice of a tired sysop. “Message 12 is not here. It may have been on the other BBS.” Exit codes stay numeric and stable. The joke is only the sentence. The failure mode is translating that sentence, or having scripts match it. So the sentence stays on stderr beside the real error, never instead of it, and --sysop would be the flag on existing commands rather than a new parser. Even that is probably one flag too many.

ftnt weather ZONE:NET/NODE

Looks at an exported base and reports how long ago that address last spoke, which echoes it still appears in, and whether its clock seems to live in 1980. It is haunt for one node, dressed as a forecast. “Node 2:236/77: overcast, last seen 400 days ago, chance of a PID from GoldED.” Genuinely charming for a blog post. A bad idea in the same binary as delete, because the name does not say it is read-only and people will type addresses at it expecting the network to answer.

ftnt palimpsest

Show every revision a message has ever had. The libraries store a revision for what is there now, not a stack of former bodies. Unless a format package grows a history, palimpsest can only print the current revision and a note that there is no earlier layer. That note is the whole command. Shipping it would advertise a memory the base does not have.

12

Agents

ftnt heads, ftnt catalog and --json-errors are built. The retry flag below is still a proposal.

An agent is a caller with a small context window, no patience for --help, and a habit of retrying. The commands are already close: JSON on stdout, stable exit codes, no prompts. heads looks around without dragging every body into the prompt. catalog is the contract for the binary that is running.

ftnt heads BASE --format jam

One JSON object per message, in number order, with the body left out. Enough to choose: msgno, from, to, subject, posted_at, board, a byte length for body_text, and MSGID when the reader already parsed one. Nothing else. The agent then calls read for the one number it actually needs, or read --body when it only wants the text.

export is the wrong tool for that first look. A busy echo will spend the window on seen-by lines and signatures before the agent has decided which message mattered. heads is allowed to be lossy. It is an index, not an archive, and it says so by what it omits.

--limit and --after MSGNO keep a long base pageable. The default limit should be finite. An agent that asks for “the base” should not be handed ten thousand subjects in one pipe unless it passed --limit 0 on purpose. Exit status matches export: 0 for a complete index, 7 if archive-style reader issues were collected under --archive.

ftnt catalog

One JSON document, no base, no stdin. It describes the tool the running binary actually is: program version, schema version, the commands and their flags, the write object’s fields, the date rule per format, the exit codes, and the file sets convert would taste. An agent reads this once per version instead of scraping help text that will be reworded.

The catalog is generated from the same parser and the same tables the commands use. A hand-written brochure will drift the first time Opus even-seconds change. If sample --format opus and the catalog disagree, the catalog is the bug.

It does not include prose from this page. Proposals are not capabilities. A command listed in the catalog exists and behaves. heads appears there only after it is real.

ftnt errors as objects

Today a failure is a sentence on stderr and an integer. Exit 4 means several different rejections. An agent can branch on 2, 3, 5, 6 and 7. It cannot branch on “odd second” versus “unknown charset” without reading English.

When stderr is not a terminal, or when --json-errors is set, each failure is one JSON object: schema_version, type: error, a stable string code, the exit status, input_record and committed when a write has those, and the same sentence a human sees in message. The sentence may change. The code may not, within a major version. Codes stay specific and few: input.structure, input.date, input.charset, base.missing, base.exists, message.missing, lock.timeout, revision.conflict, writer.rejected, reader.failed, io.failed.

Stdout is untouched. A write that committed two messages and then failed still prints two receipts, then the error object. Scripts that only understood the integer keep working. Scripts that parse stderr sentences will break if the default becomes JSON, so the default stays prose on a terminal and the JSON form is the switch an agent turns on.

Retries

The dangerous agent habit is running write again after a broken pipe or a timeout. The receipt may have been lost and the message stored. external_id is already the MSGID. A --skip-existing-msgid on write and on convert --apply makes the retry boring: if that MSGID is already in the destination, print a receipt with skipped: true and do not append. Absent MSGID, absent skip. The command does not invent an idempotency key the message did not carry.

That flag is the agent feature most likely to surprise a human who wanted two copies of the same netmail. It stays off unless named. catalog documents the default.

13

If only three get built

sample first. It is small, it locks the date rules to something you can run, and it makes every later example honest.

convert second, preview before --apply, because that is the workflow the six commands almost provide and deliberately do not.

update third, revision required, because append-only stops being enough the first time a fixture needs a corrected kludge. delete can wait until update exists and the receipt style is already boring.

Lint, thread, stat and witness are the next shelf. They are reads, they compose with what export already means, and they are hard to regret. For an agent caller, heads and catalog belong on that same shelf: one lets it see the base, the other lets it see the tool. The crooked shelf waits. The toys stay on this page.
